<p>线路规划最怕的不是预算不够，而是上线前一天才发现某个账号还没定出口、主备关系也没想清楚。把这件事当成一个倒排项目来做，节奏会稳很多：下单前七天盘点，前三天定主备，前一天把切换动作写死，上线当天只做验证，之后按 24 小时、7 天、30 天三次复盘。这条时间线适用于三五个账号的小团队，也适用于几十个账号的协作场景。</p>

<h2>一条倒排时间线：从下单前七天走到上线后一个月</h2>
<p>倒排的好处是每个节点都有明确产出物，而不是「差不多配好了」。产出物建议就三样：一张账号与出口的对应表、一份主备切换步骤、一份上线后的观察记录。三样齐了，后面换人接手也不会断档。</p>
<p>时间粒度不必精确到小时，按天推进即可。真正需要精确的是切换演练，那一步要挑业务低峰做，避免演练本身造成中断。</p>

<h2>T-7 到 T-4：盘账号、定分组、画出口地图</h2>
<p>先列账号清单，按「业务归属 + 使用人 + 注册地区」三维打标。分组粒度建议以业务线为主、使用人为辅：同一业务线的账号共用一套出口策略，使用人变动时不至于牵动全局。分组太细会让端口和预算迅速膨胀，太粗则一旦出问题影响面过大。</p>
<p>接着画出口地图：每个分组对应哪个国家、哪个城市、哪一类出口（静态独享、静态共享、动态池），写在一张表里。这张表是后续所有配置的唯一依据，改动必须走变更记录，否则三个月后没人说得清某个账号当初为什么绑在那个地区。</p>

<h3>分组粒度怎么定</h3>
<p>一个实用判断：如果两个账号的运营人、内容方向、活跃时段都不同，就分到两组；如果只是同一批人维护的多个号，可以合并到一组共用出口策略，但出口 IP 仍建议一号一出口。分组管的是策略，出口管的是身份，两者不要混为一谈。</p>

<h3>出口地图要写到城市级</h3>
<p>只写国家不够。同一国家的不同城市，运营商和网段都不同，账号资料里的城市信息若与出口城市长期不一致，属于不必要的矛盾点。地图里至少三列：账号标识、出口城市、对应线路编号。</p>

<h2>T-3 到 T-1：把主备关系和切换动作写死</h2>
<p>主备不是「再买一条线放着」，而是明确三件事：什么条件触发切换、由谁执行、切换后账号与出口的对应关系怎么改。条件要可观测，例如「连续 5 分钟探测失败」或「晚高峰丢包超过 5%」，而不是「感觉卡了就换」。</p>
<p>切换动作建议只保留三个开关：客户端侧切换代理配置、DNS 与本地缓存清理、业务侧确认新出口 IP。三步按顺序执行，每步有验证方式，避免漏掉缓存导致的「明明换了线却还走旧出口」。</p>

<h3>三种主备形态的取舍</h3>
<p>冷备最省钱，故障时才启用，代价是切换耗时可能十几分钟；温备常在线但不承载正式流量，切换快但要多付一份钱；热备两条线同时可用、按权重分流，切换近乎无感但成本最高。多数团队选温备，性价比更好。</p>

<h3>演练要真换一次线</h3>
<p>演练不是看配置写得对不对，而是真的把主线路摘掉，观察业务是否在预期时间内恢复。演练时记录三个时间点：发现时刻、执行时刻、恢复时刻。三者之差就是你的真实恢复能力，比任何 SLA 承诺都可靠。</p>

<h2>上线当天：先验证出口，再开业务</h2>
<p>上线当天的动作要克制，只做验证，不做优化。先在每个环境里查一次出口：<code>curl -x 代理 https://ipinfo.io/json</code>，把 ip、city、org 三项截图存档；再跑一次真实业务的最短闭环（登录、一次短对话、一次长文生成），确认没有异常提示。</p>
<p>浏览器和脚本要分别验证。浏览器容易因为插件或系统代理残留走错线路，脚本则容易因为环境变量未生效而直连。两边都过了，再逐步放开使用人数，不要一上来全员切过去。</p>

<h3>把验证结果留在同一个地方</h3>
<p>截图、命令输出、时间戳统一放进一个目录或一篇文档。之后出现争议时，这份记录是最省事的证据，也能帮助服务商快速定位是线路问题还是本地配置问题。</p>

<h2>上线后 24 小时、7 天、30 天各看一次</h2>
<p>24 小时看稳定性：掉线次数、重连是否成功、失败请求是否集中在某个时段。7 天看趋势：晚高峰延迟与丢包是否稳定，用量是否接近套餐上限。30 天看成本与结构：哪些分组用得多、哪些端口长期闲置、续费前是否需要调整规格。</p>
<p>三次复盘各写一句话结论即可，例如「晚高峰延迟较基线高 40%，可接受」「某分组用量占七成，下月单独升配」。结论写下来，下一次采购就有依据，不用从头再盘一遍。</p>

<h3>什么时候该调整分组</h3>
<p>出现以下信号就值得重排：某个分组连续两周用量占比超过 60%；新增业务与既有分组的使用时段完全重叠导致互相挤占；人员变动后同一出口被两个不相关的人共用。调整时先改地图再改配置，顺序反了容易漏。</p>

<h2>常见问答</h2>
<h3>只有三个账号，也需要做主备吗？</h3>
<p>答：可以简化成冷备，把备用线路的配置提前写好、账号与出口的对应关系留一行备注即可，不必长期付费。关键是故障时有人知道去哪拿配置、多久能切完，这比有没有常在线备用线更重要。</p>
<h3>倒排时间线一定要七天吗？</h3>
<p>答：七天是给「账号多、需要协调多人」的场景留的缓冲。单人维护两三个账号，压缩到两三天也可行，但盘点、演练、验证这三步不要省，省掉的那一步通常会在上线第一周以故障的形式补回来。</p>
<h3>切换后账号会不会因为出口变化产生异常提示？</h3>
<p>答：短时间内出口大幅跳变可能引起额外的验证。建议把切换安排在业务低峰，切换后先做一次常规操作再恢复正常节奏；备用出口尽量与主要出口同区域，减少地区跨度。</p>
<h3>演练会影响正在使用的账号吗？</h3>
<p>答：会短暂影响。所以演练要挑低峰时段，并提前通知使用人。若无法接受任何中断，可先用一个非核心账号做单点演练，验证切换步骤本身是否可行，再决定是否全量执行。</p>
